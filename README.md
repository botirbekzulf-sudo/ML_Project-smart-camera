# DevicePrice — определение цены техники и ценового класса смартфона

Учебный проект: фронтенд на HTML/JS со сканером камеры + backend на
Python (Flask) с ML-моделью, которая определяет ценовой класс
смартфона по характеристикам.

## Структура

```
smart-price-classifier/
├── frontend/              # HTML/CSS/JS сайт
│   ├── index.html
│   ├── scan.html          # страница со сканером камеры
│   ├── css/style.css
│   └── js/

│       └── api.js         # запросы к backend
```

## Быстрый старт

```bash
pip install -r requirements.txt
cd backend
python app.py
```

Открой `http://localhost:5000` в браузере.

Модель `price_model.pkl` уже лежит в репозитории — она обучена на
**синтетическом тестовом датасете** (`data/sample_mobile_prices.csv`),
поэтому весь сайт сразу работает и точность там неестественно высокая
(это не реальные данные). Для настоящего проекта — см. следующий шаг.

## Как подключить настоящий датасет

1. Скачай один из датасетов (регистрация на Kaggle/HuggingFace бесплатная):
   - **Kaggle — Mobile Price Classification** (классика, 2000 строк, 20
     признаков): https://www.kaggle.com/datasets/iabhishekofficial/mobile-price-classification
   - Зеркало на HuggingFace: https://huggingface.co/datasets/kheejay88/phone_price_classification_train
   - Более крупный, с реальными брендами и датами (15 000 строк, нужно
     самому сделать биннинг цены на 4 класса): https://www.kaggle.com/datasets/shraddha4ever20/smartphone-specifications-dataset

2. Сохрани CSV как `data/mobile_price_train.csv`. Обязательные столбцы —
   те же 20 признаков + `price_range` (0-3), см. `backend/ml_module/preprocess.py`
   → `FEATURE_ORDER`. Если используешь датасет с другими названиями
   столбцов — переименуй их под этот список.

3. Переобучи модель:
   ```bash
   cd backend/ml_module
   python train_price_model.py
   ```
   Скрипт сам подхватит `data/mobile_price_train.csv` вместо тестового
   и выведет accuracy, отчёт по классам и важность признаков.

## Локальная CV-модель (не используется по умолчанию)

Раньше распознавание категории устройства по фото делала своя
transfer-learning модель на MobileNetV2 — `backend/cv_module/device_classifier.py`.
Сейчас сайт вместо неё показывает карточку "Что видит Gemini 3.6"
(мультимодальный запрос к Gemini, см. раздел выше) — эту работу теперь
делает Gemini, а не локальная модель, и `app.py` её больше не вызывает.

Файл `device_classifier.py` оставлен в проекте как рабочий пример на
будущее: если понадобится офлайн-вариант без внешнего API (или чтобы не
платить за запросы к Gemini на каждый кадр), можно снова подключить его
в `app.py` вместо `/api/gemini-vision` — там же в комментариях описано,
как собрать датасет и обучить модель.

## Поиск в Google

По умолчанию (без API-ключей) сайт просто открывает обычный поиск
Google по названию модели в новой вкладке — это то, что описано в
задании. Для автоматического получения характеристик без участия
пользователя можно подключить Google Custom Search API — инструкция
и переменные окружения `GOOGLE_API_KEY` / `GOOGLE_CSE_ID` описаны в
`backend/google_search.py`.

## Чат с Gemini 3.6 — только про характеристики

`backend/gemini_assistant.py` подключает Gemini 3.6 Flash с жёстким
системным промптом: ассистент отвечает **только** про технические
характеристики устройства, которое сейчас на экране. Про цену,
"стоит ли покупать", наличие в магазинах — не отвечает по существу и
предлагает посмотреть в Google.

1. Получи API-ключ: https://aistudio.google.com/apikey
2. Установи переменную окружения `GEMINI_API_KEY` (локально — в
   `.env`/переменных окружения, на Railway — в Settings → Variables).
3. Опционально `GEMINI_MODEL` (по умолчанию `gemini-3.6-flash`).

Без ключа сайт продолжает работать как обычно — карточка чата просто
вернёт понятную ошибку вместо ответа.

## Gemini 3.6 — сканер (мультимодально) и фильтр поиска

`backend/gemini_assistant.py` использует Gemini 3.6 Flash в двух местах:

1. **Сканер (`/api/gemini-vision`)** — каждый кадр с камеры (каждые 3
   секунды, пока открыта страница сканера) уходит в Gemini мультимодально.
   Gemini коротко описывает, что видит на фото — это и есть карточка
   "Что видит Gemini 3.6" прямо на сайте. Промпт: `DEVICE_PHOTO_PROMPT`
   в `backend/gemini_prompts.py`.
2. **Фильтр поиска (`/api/lookup`)** — перед тем как сайт откроет Google
   и запустит ML-предсказание ценового класса, Gemini проверяет, что
   введённый текст похож на название электронного устройства. Промпт:
   `DEVICE_VALIDATION_PROMPT` в том же файле.

Настройка (общая для обоих):
1. Получи API-ключ: https://aistudio.google.com/apikey
2. Установи переменную окружения `GEMINI_API_KEY` (локально — в
   `.env`/переменных окружения, на Railway — в Settings → Variables).
3. Опционально `GEMINI_MODEL` (по умолчанию `gemini-3.6-flash`).

**Разное поведение без ключа:** фильтр поиска работает в режиме
"fail-open" (без ключа проверка молча пропускается, поиск идёт как
обычно). Сканер фото без ключа честно покажет в карточке "Gemini
недоступен: ..." — эта часть сайта требует ключ, чтобы работать.

**Правишь промпты — не логику.** Весь текст, который уходит в Gemini,
вынесен в отдельный файл `backend/gemini_prompts.py`. Меняй формулировку
прямо там и перезапускай сервер; `gemini_assistant.py` трогать не нужно
(только если меняешь сам формат ответа модели — тогда поправь ещё и
`_parse_validation_response()`).
